# Skill更新手順

## この文書について

この文書は、講座概要作成Skillの内容を安全に更新し、ChatGPT WorkとローカルCodexの利用者へ反映する手順をまとめたものです。

Skill IDは`course-overview-generator`、共有元は`kogureatsushi-hue/dmm-ai-lecture-guidance`です。ブランチ保護、レビュー担当者、リリース方法は初回運用時に確定します。

## 基本方針

- GitHubのPrivateリポジトリを正本とする。
- プラグインの正式名称は「DMMビジネスAI研修｜講座概要作成プラグイン」とする。
- 利用者全員にリポジトリの閲覧権限を付与し、手順書、Skill、更新履歴を自分で確認できるようにする。
- 書き込み権限は管理者と更新担当者に限定する。
- 利用者の端末へインストールされたSkillを直接編集しない。
- 変更はブランチで作業し、レビュー後にmainへ反映する。
- 共通ルールと講座固有情報を分ける。
- サンプルを正解データとして固定せず、Skillのルールと資料の根拠を優先する。
- ChatGPT WorkとローカルCodexの両方で動作を確認する。
- 出力形式に影響する変更では、MDだけでなくDOCXの見た目も確認する。

## アクセス権と役割

管理者とのリアルタイム連携を前提にせず、GitHub上の情報だけで導入状況と更新内容を確認できる運用にします。

| 役割 | GitHub権限 | 主な作業 |
|---|---|---|
| リポジトリ管理者 | 管理 | 利用者招待、権限管理、ブランチ保護、リリース管理 |
| Skill更新担当者 | 書き込み | ブランチ作成、Skill更新、テスト、Pull Request作成 |
| レビュー担当者 | 書き込みまたはレビュー | 変更内容、テスト結果、出力品質の確認 |
| ChatGPT Work管理者 | 原則閲覧 | マーケットプレイスのインポート、同期、利用ポリシー設定 |
| 一般利用者 | 閲覧 | README確認、Skill導入、更新確認、Issue報告 |

### 新しい利用者を追加する手順

1. リポジトリ管理者が対象者をPrivateリポジトリへ招待する。
2. 対象者がGitHubの招待を承認する。
3. 対象者がREADMEと利用環境別の手順書を閲覧できることを確認する。
4. ChatGPT Work利用者は、管理者がプラグインを利用可能にしていることを確認する。
5. ローカルCodex利用者は、リポジトリをcloneまたはダウンロードしてSkillを導入する。
6. 対象者がSkill一覧と動作確認用プロンプトで有効化を確認する。

ChatGPT Workへのマーケットプレイスの初回インポートと利用ポリシー設定は、ワークスペース管理者が事前に行います。以後の利用者は、READMEに記載された状態を確認し、自分でインストールと動作確認を進めます。

### READMEへ掲載する運用情報

利用者が管理者へリアルタイムに問い合わせなくても判断できるよう、READMEには次を掲載します。

- GitHubの招待を受けてから利用開始するまでの流れ
- ChatGPT WorkとローカルCodexの利用手順へのリンク
- プラグイン名「DMMビジネスAI研修｜講座概要作成プラグイン」と、現在のSkill名
- 最新バージョンと最終更新日
- ChatGPT Workへのインポート・同期状況
- 既知の問題と回避方法
- 問い合わせ先またはIssueの作成方法
- 動作確認用プロンプト

~~~text
<repository>/
├ .agents/

│     └ marketplace.json
├ plugins/

│     │  └ plugin.json
│     └ skills/
│        └ course-overview-generator/
│           ├ SKILL.md
│           ├ references/
│           ├ assets/
│           └ scripts/
├ examples/
├ docs/
├ CHANGELOG.md
└ README.md
~~~

## ファイルごとの役割

| 変更内容 | 主な更新先 |
|---|---|
| Skillを使う条件、入力、処理順、質問・停止条件 | SKILL.md |
| 講座概要の構成、タイムテーブル規則、確認基準 | references/ |
| MD・DOCXのひな形、スタイル、固定部品 | assets/ |
| 時間計算、DOCX変換、検証などの確定処理 | scripts/ |
| 完成イメージ、回帰確認用データ | examples/ |
| 利用者・管理者向け手順 | docs/、README.md |
| プラグイン名、バージョン、同梱Skill | .codex-plugin/plugin.json |
| GitHubから配布するプラグイン一覧 | .agents/plugins/marketplace.json |

同じ規則を複数ファイルへ重複記載しないようにします。詳細規則はreferencesへ置き、SKILL.mdから「いつ読むか」を指定します。

## 更新が必要になる例

- 講座概要の見出しや表形式を変更するとき
- 3時間・2時間講座以外の時間ルールを追加するとき
- 演習とハンズオンの判定方法を変更するとき
- 質問するタイミングや確認ゲートを変更するとき
- 新しいDOCXテンプレートへ差し替えるとき
- Google Driveの確認・保存手順を変更するとき
- ChatGPT WorkまたはCodexの仕様変更へ対応するとき
- 出力漏れや誤動作を修正するとき

## 更新手順

### 1. 変更内容を記録する

更新前に、次の項目をIssueまたは作業メモへ記録します。

- 現在の問題
- 期待する動作
- 変更対象
- 影響する利用環境
- 確認に使う講座資料
- 完了条件

不具合の場合は、再現した入力、実際の出力、期待する出力を残します。講座資料に機密情報がある場合は、Issueへ直接添付せず、アクセス制限された保存場所を示します。

### 2. 最新版を取得する

~~~bash
git switch main
git pull --ff-only
~~~

ローカルに未コミットの変更がある場合は、先に内容を確認します。利用者の変更を破棄する操作は行いません。

### 3. 作業ブランチを作成する

~~~bash
git switch -c update/<short-description>
~~~

例：

~~~bash
git switch -c update/timetable-validation
~~~

### 4. 変更先を決める

次の基準で、編集する場所を選びます。

- Skillの発動条件や処理順を変える：SKILL.md
- 判断基準や文章ルールを変える：references
- 見た目や定型フォーマットを変える：assets
- 毎回同じ結果が必要な計算・変換を変える：scripts
- 使い方だけを直す：docsまたはREADME

講座固有のAIモデル名、プラン制限、製品バージョン、注意事項などは、原則として共通ルールへ直接書きません。「資料から抽出し、確認できなければ質問する」という判断規則を共通化します。

### 5. Skill Creatorを使って更新する

Skillの指示内容や構成を変更する場合は、Skill Creatorを利用できます。

ChatGPT Workでは「@skill-creator」、Codexでは「$skill-creator」を指定します。

~~~text
既存のcourse-overview-generator Skillを更新してください。

変更理由：＜理由＞
期待する動作：＜動作＞
変更対象：＜SKILL.md、reference、asset、scriptなど＞
維持する動作：MD確認前にDOCX化しないこと
確認ケース：＜使用するサンプル＞
~~~

生成結果はそのまま採用せず、変更差分と既存ルールへの影響を確認します。

### 6. 構文と構成を確認する

最低限、次の点を確認します。

- SKILL.mdの先頭にnameとdescriptionがある。
- descriptionだけで利用場面と対象外が判断できる。
- 入力、処理、出力、質問条件、停止条件が明記されている。
- references、assets、scriptsへのパスが正しい。
- 存在しないツールやファイルを前提にしていない。
- プラグインのmanifestとマーケットプレイスのJSONが有効である。
- 秘密情報、個人情報、認証情報を含んでいない。

### 7. 動作テストを行う

次の5種類を必ず確認します。

| テスト | 確認内容 |
|---|---|
| 明示呼び出し | Skill名を指定した依頼で正しく動く |
| 間接呼び出し | Skill名がなくても対象業務を認識できる |
| 不完全な入力 | 不足情報を推測せず質問できる |
| 対象外の依頼 | 関係のない依頼で誤作動しない |
| 境界ケース | 矛盾、欠損、複数版がある場合に安全に止まれる |

講座概要については、Day1・Day2または同等の回帰確認用サンプルで次を検証します。

- PDFとワークファイルの両方を確認している。
- 「講座の概要」「章構成」「タイムテーブル」「ポイント」「注意点」がある。
- 演習とハンズオンが区別されている。
- 演習名と受講生の実施時間が内容列にある。
- 未確定の演習時間だけを仮置きし、利用者へ確認している。
- 講座全体、休憩、各区分の時間が一致している。
- MDの承認前にDOCXを作成していない。
- 資料にない講座固有情報を追加していない。
- DOCXの表、改ページ、見出し、余白が崩れていない。
- 指定した保存先以外へ書き込んでいない。

### 8. 文書とサンプルを更新する

利用方法や出力形式が変わる場合は、README、利用手順、完成サンプルも同じ変更内で更新します。

サンプルだけを修正して、Skillやreferenceの規則を直さない状態を残さないようにします。サンプルへ講座固有の例を追加した場合は、それが共通ルールではないことを明記します。

### 9. バージョンと変更履歴を更新する

プラグインはセマンティックバージョニングを基本とします。

| 種別 | 例 | バージョン |
|---|---|---|
| 誤字、説明補足、互換性のある小修正 | 1.0.0 → 1.0.1 | PATCH |
| 新しい入力形式、検証機能、任意機能の追加 | 1.0.0 → 1.1.0 | MINOR |
| 必須入力や出力形式の非互換変更 | 1.0.0 → 2.0.0 | MAJOR |

「.codex-plugin/plugin.json」のversionと「CHANGELOG.md」を更新します。変更履歴には、変更点、利用者への影響、移行作業の有無を記載します。

### 10. コミットしてPull Requestを作成する

~~~bash
git status
git diff
git add <変更したファイル>
git commit -m "Update course overview workflow"
git push -u origin update/<short-description>
~~~

Pull Requestには次を記載します。

- 変更理由
- 変更したファイル
- 変更前後の動作
- 実施したテスト
- MDとDOCXの確認結果
- 利用者への影響
- ロールバック方法

### 11. レビューしてmainへ反映する

レビュー担当者は、文章の自然さだけでなく、資料の根拠、時間計算、確認ゲート、他講座への影響を確認します。

承認後にmainへマージします。重要なリリースではGitタグを作成し、戻せる版を明確にします。

### 12. 利用者向け情報を更新する

mainへ反映したら、READMEの最新バージョン、最終更新日、ChatGPT Workの同期状況、既知の問題を更新します。

一般利用者はリポジトリを閲覧できるため、変更内容と必要な作業をGitHub上で確認できます。再インストール、Codex再起動、入力形式の変更など利用者側の対応が必要な場合は、READMEとCHANGELOGの両方に明記します。

## 利用環境への反映

### ChatGPT Work

GitHubからマーケットプレイスをインポートしている場合、ワークスペース側の同期により更新されます。すぐに反映したい場合は、管理者が管理画面の対象マーケットプレイスから「Sync now」を実行します。

同期後は、「DMMビジネスAI研修｜講座概要作成プラグイン」のバージョン、インストールポリシー、必要なGoogle Driveプラグインの利用可否を確認します。更新によって新しい権限が必要になった場合は、利用者へ事前に案内します。

### ローカルCodex

リポジトリをクローンして利用している場合は、最新版を取得します。

~~~bash
git switch main
git pull --ff-only
~~~

Skill Installerまたはコピーで導入した場合は、変更内容を確認してから再インストールします。変更が認識されない場合はCodexを再起動します。

## ロールバック

更新後に問題が見つかった場合は、main上のファイルを直接書き戻さず、修正用Pull Requestまたはrevertを使用します。

1. 影響範囲を確認する。
2. 問題が発生したバージョンを特定する。
3. 直前の安定版タグまたはコミットを確認する。
4. revert用ブランチとPull Requestを作成する。
5. 回帰テストを行う。
6. mainへ反映し、ChatGPT Workを再同期する。
7. 変更履歴に原因と対応を記録する。

## 更新時に行わないこと

- mainブランチを直接編集する。
- 利用者の端末にあるSkillだけを修正する。
- Day1・Day2固有の内容を共通ルールへ無条件に追加する。
- 根拠のない仕様を「標準」として追加する。
- 確認ゲートを省略し、MDから自動的にDOCXを公開する。
- 認証情報、共有リンクの秘密情報、個人情報をコミットする。
- 権利確認なしに講座PDFやワーク素材をリポジトリへ追加する。
- テストせずにプラグインのバージョンだけを更新する。
